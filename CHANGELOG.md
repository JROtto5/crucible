- 2026-11-07: `crucible anchor-replay` measures whether the verifier should see the reviewer's argument. It never has: it gets the claim and its falsification test, not the reviewer's `problem`/`fix` text. The command re-verifies findings the author has answered (refuted = false alarm, fixed/deferred = real) at the commit they were raised on, once with today's prompt and once with the argument added. It compares the two over the findings both arms judged and reports the cost. Commits come from local clones via a temp repo that borrows the clone's object store, so amended-away rounds and partial clones work and the clone is never written to. Replayed verdicts go to a throwaway cache. The default prompt is byte-identical, so cached verdicts stay valid, and no eval was needed. First run, on 20 of the 56 answered code findings (10 refuted, 10 held up), $2.32: without the argument, 5/10 false alarms kept and 1/10 real findings dropped; with it, 6/10 and 1/10. The 3 disagreements flip both ways, two of them on near-identical Lutris findings, so the gap is noise and the prompt stays as it is. A second number came out of it: a plain re-verification dropped 5 of the 10 findings authors later refuted, all of which had been kept the first time. Tests 172 → 181 (prompt, finding selection, sampling, paired tally, CLI wiring, commit lookup, partial-clone checkout, end-to-end run; the paired tally, the partial-clone checkout and the sampling order each fail on the code they replaced).
